# Исследования и Технический Анализ (Research)

## 1. Механизм перехвата WebRTC-аудио (WebRTC Interception)

Яндекс.Телемост использует стандарт WebRTC для передачи медиаданных между участниками в реальном времени. В Chromium-подобных браузерах обмен потоками происходит через объект `RTCPeerConnection`. 

Для перехвата аудио в [recorder.js](file:///e:/telemost/recorder.js) внедряется JavaScript-код на этапе инициализации новой веб-страницы с помощью функции `page.evaluateOnNewDocument`.
- Патчится глобальный конструктор `window.RTCPeerConnection`.
- При добавлении удаленных треков через событие `track`, треки с типом `audio` сохраняются в массив.
- Создается `AudioContext` и узел `MediaStreamAudioDestinationNode`.
- Все перехваченные аудиодорожки подключаются как источники (`createMediaStreamSource`) к общему микшеру.
- Смешанный аудиопоток записывается через API `MediaRecorder` с MIME-типом `audio/webm;codecs=opus` и битрейтом 32 kbps.
- Каждые 2 секунды чанки в формате Base64 передаются в Node.js через экспортированную функцию `__saveAudioChunk` и дописываются в файл.

## 2. Лимиты провайдеров транскрибации

### AssemblyAI (Основной)
- **Преимущество**: Отличная точность распознавания русского языка и встроенная диаризация (определение спикеров).
- **Лимиты**: Позволяет отправлять аудиофайлы размером до 5 ГБ и длительностью до 10 часов напрямую.
- **Особенности**: Требует наличия действующего `ASSEMBLYAI_API_KEY`. Использование моделей `universal-3-pro` или `universal-2`.

### Groq Whisper (Резервный)
- **Преимущество**: Сверхбыстрая скорость работы Whisper-large-v3 и низкая стоимость.
- **Лимиты**: Жесткое ограничение на максимальный размер загружаемого файла в **25 МБ**.
- **Решение**: Нарезка аудио с помощью FFmpeg на чанки. При длине чанка в 10 минут (600 секунд) файл с битрейтом 32 kbps гарантированно укладывается в ~2.4 МБ, что значительно ниже лимита.

## 3. Локальное сегментирование через FFmpeg

В [services/ffmpeg.js](file:///e:/telemost/services/ffmpeg.js) реализована функция `segmentAudioIfNecessary`.
- Она проверяет размер локального `.webm` файла.
- Если размер превышает 24.5 МБ, запускается утилита `ffmpeg`.
- Для оптимизации производительности нарезка осуществляется с флагами `-f segment -segment_time 600 -c copy`. Флаг `-c copy` указывает копировать кодек без перекодирования звука, что снижает нагрузку на CPU сервера практически до нуля и работает мгновенно.
- Результатом работы является список пронумерованных чанков в папке `./recordings/.../chunks/`, которые затем обрабатываются в цикле последовательно.

## 4. Жизненный цикл контейнера и защита от зомби-процессов

При автоматическом запуске в Docker Puppeteer запускает экземпляр Chromium в фоновом режиме. Если Node-процесс завершается некорректно (например, при сбое или принудительном убийстве контейнера), Chromium остается работать в памяти в качестве "зомби", потребляя значительные ресурсы.

Для устранения этой проблемы:
1. Внедрена обертка `try...finally` в основной поток `recorder.js`, гарантирующая вызов `await browser.close()`.
2. Настроены обработчики сигналов `SIGINT` и `SIGTERM` в `process.on(...)`. При их получении вызывается функция `gracefulShutdown`, которая корректно завершает `MediaRecorder` (записывая финальные метаданные WebM, предотвращая порчу файла) и закрывает Chromium.

## 5. Экспериментальная гипотеза: Локальная диаризация на базе WebRTC-треков

### Описание гипотезы
Каждый удаленный участник встречи Яндекс.Телемост передает свой собственный аудиопоток, поступающий в браузер как отдельный `MediaStreamTrack`. 
Если мы будем анализировать активность (амплитуду/громкость) каждого трека отдельно в реальном времени, мы сможем построить точную временную шкалу реплик спикеров непосредственно в процессе записи, полностью исключив необходимость использования внешних дорогостоящих ИИ-моделей диаризации (например, AssemblyAI Speaker Labels).

### Технологический стек эксперимента
- **Web Audio API (`AnalyserNode`)**: Создается для каждого входящего трека. Позволяет замерять частотную и амплитудную характеристики с помощью метода `getByteFrequencyData` каждые 100-200 мс.
- **Интеграция с DOM Телемоста**: Сопоставление `track.id` с HTML-элементом `<audio>` и восходящий поиск родительских контейнеров в сетке участников для считывания имени спикера (позволяет отображать в транскрипте реальное имя участника, а не абстрактное `Спикер 0`).
- **Формат артефакта**: Локальный файл `diarization_map.json`, содержащий временные диапазоны активности треков:
  ```json
  [
    { "start": 12.4, "end": 18.2, "speaker_name": "Иван Иванов" }
  ]
  ```

### Методика тестирования
Для изолированного тестирования гипотезы создан экспериментальный скрипт [test_tracks.js](file:///C:/Users/igor/.gemini/antigravity-ide/scratch/test_tracks.js), который запускает Puppeteer в режиме `headless: false`, внедряет анализатор громкости на каждый удаленный аудио-трек и логирует активность в консоль при превышении порога тишины.

## 6. Анализ фичи кастомизации имени бота (BOT_DISPLAY_NAME)

### Как устроено сейчас
В проекте присутствует вспомогательный скрипт [set_recorder_display_name.sh](file:///e:/telemost/set_recorder_display_name.sh), предназначенный для изменения имени бота. Скрипт принимает новое имя в качестве аргумента и перезаписывает переменную `BOT_DISPLAY_NAME` в файле `.env` на хост-сервере.

### Выявленные проблемы и ограничения (Недореализованная фича)
1. **Отсутствие проброса в контейнер**: Скрипт запуска контейнера [run_join.sh](file:///e:/telemost/run_join.sh#L24-L31) не пробрасывает переменную `BOT_DISPLAY_NAME` в команду `docker run` (отсутствует флаг `-e BOT_DISPLAY_NAME`), а также не монтирует файл `.env` внутрь контейнера. В результате Chromium внутри контейнера всегда использует дефолтное значение имени (`Telemost Recorder` или `Бот-Ассистент`), зашитое в образ при его сборке, полностью игнорируя настройки пользователя.
2. **Нарушение многопользовательской изоляции (Race Condition)**: Поскольку имя сохраняется в глобальный файл `.env` на хост-сервере, любые изменения имени одним пользователем мгновенно перезаписывают глобальную настройку. При одновременном запуске записей несколькими пользователями с разными именами ботов возникнет состояние гонки, и боты зайдут во встречи с некорректными (чужими) именами.

### Рекомендуемое архитектурное решение
- Настройки имени бота должны сохраняться в PostgreSQL базе данных n8n для каждого конкретного `chat_id` пользователя.
- При запуске записи оркестратор n8n должен извлекать имя из БД и передавать его третьим аргументом в скрипт запуска на сервере: `./run_join.sh <URL> <CHAT_ID> "<DISPLAY_NAME>"`.
- Скрипт `run_join.sh` должен считывать этот аргумент и пробрасывать его в контейнер через переменную окружения:
  ```bash
  DISPLAY_NAME="${3:-Бот-Ассистент}"
  docker run -d ... -e BOT_DISPLAY_NAME="$DISPLAY_NAME" ...
  ```

## 7. Анализ логики запуска и многопользовательской оркестрации (Параллельные записи и предотвращение дубликатов)

### Ограничение на одну запись на пользователя
В текущей реализации имя контейнера жестко привязано к ID чата: `CONTAINER_NAME="telemost_$CHAT_ID"`. При старте новой записи скрипт `run_join.sh` останавливает и удаляет любой запущенный контейнер с таким именем:
```bash
docker stop "$CONTAINER_NAME" 2>/dev/null
docker rm "$CONTAINER_NAME" 2>/dev/null
```
Это полностью исключает возможность для одного пользователя записывать более одной встречи одновременно.

### Проблема двойного запроса одной встречи (Дубликаты)
Повторная отправка одной и той же ссылки Телемост тем же пользователем (или другим) приводит к тому, что скрипт убивает текущую запись и запускает ее заново. Это приводит к потере уже записанного аудиофрагмента и нарушает стабильность системы.

### Рекомендуемое решение: Идентификация по ID встречи
1. **Выделение ID встречи**: Извлекать уникальный ID встречи из URL (например, `12345678901234` из ссылки `https://telemost.yandex.ru/j/12345678901234`).
2. **Уникальные имена контейнеров**: Формировать имя контейнера как `telemost_${CHAT_ID}_${MEETING_ID}`. Это позволит одному пользователю записывать несколько встреч параллельно, так как контейнеры будут иметь разные имена (например, `telemost_123_meetingA` и `telemost_123_meetingB`).
3. **Проверка дубликатов**: Перед запуском контейнера скрипт должен проверять, запущен ли уже контейнер для этой встречи (независимо от того, кто ее запустил).
   ```bash
   MEETING_ID=$(echo "$JOIN_URL" | grep -oE '[0-9a-zA-Z_-]+$')
   # Проверка по всей системе (docker ps)
   if docker ps --format '{{.Names}}' | grep -q "_${MEETING_ID}$"; then
     echo '{"error":"Duplicate", "message":"Встреча уже записывается другим процессом"}'
     exit 1
   fi
   ```
4. **Удобный UX в Telegram (Быстрый старт)**:
   - В n8n добавить триггер регулярного выражения на ссылки Телемоста (`https://telemost.yandex.ru/j/...`).
   - Если пришло сообщение, содержащее только ссылку, n8n сразу выполняет запуск записи (без необходимости выбирать команды в меню).
   - В ответ отправляется сообщение: `Запись встречи начата.` с inline-кнопкой `Остановить запись` (в callback_data кнопки передается ID встречи или ID контейнера, например `stop_[MEETING_ID]`).

## 8. Поэтапная выгрузка и интеллектуальное переименование папок на Яндекс.Диске

### Схема поэтапной выгрузки
Для надежности работы и информирования пользователя система должна выгружать данные по мере их готовности:
1. **Аудиозапись**: После завершения встречи файл `meeting_audio.webm` сразу выгружается в созданную папку с временным именем (например, `YYYY-MM-DD_[Временный_ID]`).
2. **Текстовая стенограмма**: После транскрибации файл `transcript.txt` загружается в ту же папку.

### Протокол WebDAV: Переименование папки (Метод MOVE)
Для смены имени папки на Яндекс.Диске используется HTTP-метод `MOVE`. Запрос должен содержать заголовок `Destination` с новым путем:
```http
MOVE /Yandex.Telemost.Records/2026-06-20_tempID HTTP/1.1
Host: webdav.yandex.ru
Authorization: Basic ...
Destination: /Yandex.Telemost.Records/2026-06-20_AI_Generated_Name
```

### Алгоритм генерации имени папки на основе ИИ (LLM)
Оркестратор (n8n) передает расшифрованный текст встречи в LLM. Модель подсчитывает количество уникальных спикеров и анализирует тему разговора:
- **Кейс 1 (Спикеров от 2 до 4)**: Имя формируется по шаблону `[Имя_1]_и_[Имя_2]_о_[Тема]` (например, `Павел_и_Ксения_о_разработке_бота`). Временная папка переименовывается в `YYYY-MM-DD_[Сгенерированное_Имя]`.
- **Кейс 2 (Спикеров 5 и более)**: Имя формируется по шаблону `Конференция_на_тему_[Тема]` (например, `Конференция_на_тему_оптимизации_бизнес_процессов`). Временная папка переименовывается в `YYYY-MM-DD_[Сгенерированное_Имя]`.

## 9. Исследование технологий для архивного доступа и RAG (Roadmap)

### 9.1. Сканирование архива встреч по WebDAV (PROPFIND)
Для отображения списка записанных проектов бот может опрашивать структуру Яндекс.Диска.
- WebDAV-метод `PROPFIND` с заголовком `Depth: 1` возвращает XML-документ со списком всех подпапок в `/Yandex.Telemost.Records`.
- Пример XML ответа Яндекс.Диска:
  ```xml
  <d:multistatus xmlns:d="DAV:">
    <d:response>
      <d:href>/Yandex.Telemost.Records/2026-06-20_Павел_и_Ксения/</d:href>
      <d:propstat>...prop...</d:propstat>
    </d:response>
  </d:multistatus>
  ```
- Для минимизации трафика и задержек рекомендуется дублировать список папок в локальной базе данных PostgreSQL в момент переименования, а `PROPFIND` использовать как резервный способ синхронизации.

### 9.2. Векторизация расшифровок (pgvector)
Внедрение RAG (Retrieval-Augmented Generation) позволяет чатиться со стенограммой.
- **Модель эмбеддингов**: Использование бесплатных API эмбеддингов (например, Hugging Face `all-MiniLM-L6-v2` с вектором 384 размерности) или OpenAI API `text-embedding-3-small` (1536 размерность, высокая точность).
- **PostgreSQL pgvector**:
  - Расширение устанавливается командой `CREATE EXTENSION IF NOT EXISTS vector;`.
  - Создается таблица чанков:
    ```sql
    CREATE TABLE meeting_chunks (
      id SERIAL PRIMARY KEY,
      meeting_id VARCHAR(50),
      chat_id VARCHAR(50),
      chunk_text TEXT,
      embedding vector(384) -- размерность вектора модели
    );
    ```
  - Семантический поиск по косинусному расстоянию (оператор `<=>`):
    ```sql
    SELECT chunk_text, 1 - (embedding <=> :query_embedding) AS similarity
    FROM meeting_chunks
    WHERE meeting_id = :meeting_id
    ORDER BY embedding <=> :query_embedding
    LIMIT 5;
    ```

### 9.3. Проблема мульти-контекстного RAG (Лимиты токенов LLM)
При объединении контекста нескольких длинных встреч возникает риск превышения лимитов контекста LLM.
- **Подход 1: Top-K семантический поиск по всему массиву**. Запрос пользователя векторизуется и сравнивается со всеми чанками выбранных встреч. В контекст LLM передаются только Top-10 наиболее похожих фрагментов. Каждому чанку приписывается мета-тег: `[Дата: YYYY-MM-DD | Тема: Тема | Спикеры: Имена]`. Это позволяет ИИ-ассистенту группировать ответы хронологически.
- **Подход 2: Иерархический Map-Reduce**. Поисковый запрос отправляется к отдельным встречам. Для каждой встречи генерируется локальный мини-ответ (Map), затем финальная LLM-нода суммирует все ответы в единый отчет (Reduce). Это решает проблему переполнения контекста, но требует большего числа API-вызовов.

### 9.4. Технический анализ real-time инъекции звука во встречу
Для реализации двустороннего голосового диалога бота во встрече Яндекс.Телемост необходимо решить задачу воспроизведения звука с хоста внутрь WebRTC-сессии.

#### Подмена getUserMedia в контексте страницы
Поскольку Puppeteer работает в headless-режиме, стандартный доступ к системному микрофону отсутствует. Решением является внедрение monkey-patching кода на этапе `evaluateOnNewDocument`:
```javascript
const originalGetUserMedia = navigator.mediaDevices.getUserMedia.bind(navigator.mediaDevices);
navigator.mediaDevices.getUserMedia = async function(constraints) {
  if (constraints && constraints.audio) {
    console.log("[patch] Перехват getUserMedia для инъекции аудио ИИ");
    
    const audioCtx = new (window.AudioContext || window.webkitAudioContext)();
    const destination = audioCtx.createMediaStreamDestination();
    
    // Экспонируем контекст для отправки аудиоданных из Node.js
    window.__aiAudioCtx = audioCtx;
    window.__aiAudioDestination = destination;
    
    // Если Телемост запрашивает и видео, совмещаем виртуальное аудио с реальной/пустой заглушкой видео
    if (constraints.video) {
      const videoStream = await originalGetUserMedia({ video: constraints.video });
      const combinedStream = new MediaStream([
        ...destination.stream.getAudioTracks(),
        ...videoStream.getVideoTracks()
      ]);
      return combinedStream;
    }
    return destination.stream;
  }
  return originalGetUserMedia(constraints);
};
```

#### Воспроизведение аудиопотока из Node.js в браузер
1. ИИ-агент генерирует синтезированный голос в виде бинарных аудиочанков (например, PCM или MP3).
2. Чанки пересылаются в контекст браузера через WebSocket-соединение или Puppeteer `page.exposeFunction` / `page.evaluate`.
3. Внутри браузера аудиодекодер преобразует чанки в `AudioBuffer`:
   ```javascript
   async function playAiAudioChunk(base64Data) {
     const binaryString = atob(base64Data);
     const len = binaryString.length;
     const bytes = new Uint8Array(len);
     for (let i = 0; i < len; i++) {
       bytes[i] = binaryString.charCodeAt(i);
     }
     const audioBuffer = await window.__aiAudioCtx.decodeAudioData(bytes.buffer);
     const source = window.__aiAudioCtx.createBufferSource();
     source.buffer = audioBuffer;
     source.connect(window.__aiAudioDestination);
     source.start(0);
   }
   ```
4. Звук воспроизводится внутри `AudioContext` и поступает напрямую в WebRTC-соединение встречи.

#### Анализ real-time API
Для голосового агента критически важен пинг диалога.
- **Yandex SpeechKit gRPC**: Поддерживает потоковую отправку аудио (LPCM/Opus) и потоковое получение результатов транскрибации/синтеза, обеспечивая задержку в районе 800–1200 мс.
- **OpenAI Realtime API**: Полностью WebSocket-ориентированный протокол, исключающий необходимость в сторонних TTS/STT решениях. Агент напрямую принимает сжатый звук и отвечает сжатым звуком, сводя latency к ~300-500 мс, что делает диалог неотличимым от общения с живым человеком.

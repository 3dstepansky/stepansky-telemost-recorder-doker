## Краткое описание
Технический план описывает ядро системы записи встреч Яндекс.Телемост. Захват аудиопотока выполняется через Puppeteer-бота путем внедрения (monkey patching) в объект `RTCPeerConnection` и перенаправления треков в `MediaRecorder` с сохранением в Opus WebM. Дальнейшая обработка включает отправку аудио в AssemblyAI (или нарезку через FFmpeg и отправку в Groq Whisper при сбое), загрузку результатов на Яндекс.Диск через WebDAV и S3, а также завершение по сигналам/одиночеству для исключения зомби-процессов.

## Технический контекст

**Язык/Версия**: Node.js (v20+), ES Modules (JavaScript)

**Основные зависимости**:
- `puppeteer` (^24.0.0) — управление Chromium и эмуляция пользователя.
- `assemblyai` (^4.35.0) — основная транскрибация с разделением спикеров.
- `groq-sdk` (^1.2.1) — резервная быстрая транскрибация через Whisper-large-v3.
- `axios` (^1.6.7) — HTTP-клиент для WebDAV-запросов и отправки вебхуков в n8n.
- `@aws-sdk/client-s3` (^3.500.0) — опциональная выгрузка медиа в объектные хранилища.
- `dotenv` (^16.4.5) — конфигурация переменных окружения.

**Хранилище данных**:
- Локальная файловая система: временная директория `./recordings/[Timestamp]/` для накопления аудиоданных и транскриптов.
- Внешнее облако: Яндекс.Диск (папка `Yandex.Telemost.Records/[Встреча]`) по протоколу WebDAV.
- Объектное хранилище: S3-совместимое (например, Yandex Cloud Object Storage).

**Тестирование**:
- Ручная валидация сценариев с помощью скриптов `run_join.sh`, `run_stop.sh` и `transcribe.js`.

**Целевая платформа**:
- Docker-контейнер (образ на базе Node с предустановленным Google Chrome и FFmpeg) на ОС Linux (Ubuntu 24.04).

**Тип проекта**:
- Headless Docker Worker (микросервис записи) + CLI утилиты.

**Цели по производительности**:
- Подключение бота к встрече менее чем за 15 секунд.
- Потребление ресурсов рекордером: <10% CPU и <200MB RAM на одну сессию записи.

**Ограничения**:
- Лимит на размер одного файла для Groq Whisper API составляет 25 МБ.
- Вход только под гостевой учетной записью Яндекс.Телемост (без авторизации по логину Яндекса).

## Проверка по Конституции

*Контрольная точка (GATE): Пройдена.*

- **Модульность (Separation of Concerns)**: Логика разделена. Рекордер `recorder.js` пишет аудио, `transcribe.js` занимается расшифровкой и WebDAV, а n8n координирует запуск.
- **Предотвращение зомби-процессов**: Все вызовы в `recorder.js` обернуты в `try...finally` с закрытием браузера, настроена обработка `SIGINT`/`SIGTERM`.
- **Локальная очистка**: Скрипт `transcribe.js` гарантирует очистку папки после успешного WebDAV PUT-запроса.
- **Безопасность учетных данных**: Учетные данные Яндекс.Диска передаются параметрами из n8n, на сервере статически не хранятся.

### Проектирование поэтапной выгрузки и переименования папок по WebDAV
- **Схема загрузки**: Сначала рекордер вызывает скрипт выгрузки оригинального аудио, затем после транскрибации выгружается `.txt` файл стенограммы в ту же папку.
- **Метод MOVE в `services/webdav.js`**: Реализовать функцию `renameYandexDiskFolder(oldPath, newPath)` с использованием HTTP-метода `MOVE` через Axios.
- **Интеграция с LLM (n8n)**:
  - n8n получает стенограмму и передает ее в LLM-ноду.
  - LLM извлекает список спикеров и тему встречи.
  - LLM возвращает имя в зависимости от классификации спикеров: `< 5` (формат с именами спикеров) или `>= 5` (формат конференции).
  - n8n выполняет SSH-запрос для вызова метода `MOVE` на Яндекс.Диске, переименовывая временную папку.

## Очередность и приоритеты реализации фич (Roadmap Sequence & Prioritization)

В соответствии с требованиями к стабильности результата, простоте тестирования и легкости внедрения, все перспективные фичи разделены на этапы с жесткой очередностью реализации. **Живой разговор с голосовым ИИ-агентом внутри Телемоста (как наиболее сложная и экспериментальная фича с высоким риском нестабильности) вынесен в самый конец списка и будет реализовываться в последнюю очередь.**

### Принципы планирования очередности
1. **Простота и надежность (Low Risk / High Value)**: Сначала реализуются фичи, не требующие внешних сложных API, изменений в БД или сложных real-time протоколов (например, кастомизация имени бота во встрече).
2. **Изоляция и стабильность ядра (Core Stability)**: Фичи, предотвращающие сбои рекордеров при множественном или ошибочном параллельном запуске (защита от дубликатов), имеют высший приоритет в очереди разработки.
3. **Легкость тестирования (Testability)**: Шаги выстраиваются так, чтобы каждый этап можно было проверить изолированными тестами (например, WebDAV методы в CLI, SQL миграции в локальной БД).
4. **Инфраструктурная эволюция (Infrastructure-first)**: Базовый реестр встреч в PostgreSQL внедряется до RAG-систем, так как эмбеддинги чанков жестко привязываются к метаданным встреч.

### Очередь реализации (от простых/стабильных к сложным/экспериментальным)

1. **Персональное имя бота в настройках (Phase 9)**
   - *Почему сейчас*: Очень низкая сложность. Настройка сводится к добавлению одной строки/параметра в конфигурацию запуска Chromium.
   - *Стабильность*: Высокая. Не влияет на существующую логику записи.
   - *Тестирование*: CLI-запуск с аргументами и визуальный контроль имени в Яндекс.Телемосте.

2. **Мульти-запись, быстрый старт по ссылке и контроль дубликатов (Phase 10)**
   - *Почему сейчас*: Критично для стабильности серверных ресурсов. Исключает утечки RAM от зависших дублирующих контейнеров Puppeteer при ошибочных повторных кликах пользователя.
   - *Стабильность*: Крайне высокая. Исключает race condition.
   - *Тестирование*: Автоматические bash/JS сценарии параллельного вызова, проверяющие блокировку запуска дубликатов по ID встречи.

3. **Архив встреч и кастомное переименование папок на Яндекс.Диске (Phase 12)**
   - *Почему сейчас*: Создает базовый реестр встреч в PostgreSQL и пользовательский интерфейс в Telegram для управления историей.
   - *Стабильность*: Высокая. Использует стабильные методы `GET` и `MOVE` WebDAV API.
   - *Тестирование*: Проверка SQL миграций и mock-вызовы WebDAV для перемещения и скачивания файлов.

4. **Векторизация и чат по одной встрече (RAG) (Phase 13)**
   - *Почему сейчас*: Требуется для перехода от пассивной стенограммы к интерактивной базе знаний. Зависит от реестра встреч (Phase 12).
   - *Стабильность*: Средняя (зависит от провайдера эмбеддингов и точности разбивки на чанки). Требует контроля изоляции данных по `chat_id` пользователя.
   - *Тестирование*: Скрипт валидации косинусного сходства эмбеддингов чанков одной встречи.

5. **Мульти-встречный чат и глобальный поиск (Phase 14)**
   - *Почему сейчас*: Развитие локального RAG до масштабов всей истории соавторства пользователя.
   - *Стабильность*: Средняя. Риск переполнения контекстного окна LLM. Требует внедрения алгоритмов агрегации контекста (Top-K/Map-Reduce).
   - *Тестирование*: Тесты на поиск по ключевым словам и фразам сквозь несколько независимых стенограмм.

6. **Живой голосовой разговор с ИИ-агентом внутри Телемоста (Phase 15) — [ПОСЛЕДНЯЯ В ОЧЕРЕДИ]**
   - *Почему в самом конце*: Экстремально высокая сложность. Требует real-time STT/TTS интеграций, постоянного анализа аудиопотока через VAD, поддержания WebSocket соединений с минимальной задержкой (<1.5с) и сложного monkey-patching медиа-устройств.
   - *Стабильность*: Низкая. Высокая чувствительность к сетевым задержкам и изменениям DOM-структуры WebRTC-страниц Телемоста.
   - *Тестирование*: Требует сложной симуляции голосового общения в тестовых звонках.
   - **Решение**: Проектирование и реализация этой фичи начнется только после того, как все предыдущие 5 фаз будут сданы, протестированы и переведены в статус стабильной эксплуатации.

## Проектирование перспективных фич (Архитектура)

### 1. Архитектура доступа к архиву и кастомного переименования
- **Хранение реестра**: Метаданные записанных встреч (имя папки, дата, chat_id, пути к файлам на Яндекс.Диске) дублируются в PostgreSQL для мгновенного отображения архива в Telegram-боте.
- **Интерфейс архива**: Бот при нажатии кнопки "Архив" выгружает инлайн-кнопки со списком последних 5-10 встреч. При выборе встречи бот предлагает три действия:
  - `Получить аудио` (WebDAV `GET` -> скачивание -> отправка в Telegram как Audio/Voice).
  - `Стенограмма` (WebDAV `GET` `transcript.txt` -> отправка как Text/Document).
  - `Саммари` (WebDAV `GET` `summary.txt` -> отправка как Text сообщение).
- **Кастомный Нейминг**: При запросе переименования встречи бот принимает новый текст от пользователя, валидирует его (заменяет спецсимволы), обновляет запись в PostgreSQL и отправляет WebDAV `MOVE` запрос на переименование папки проекта на Яндекс.Диске.

### 2. Пайплайн Векторизации и RAG для чата с агентом
- **Сервис эмбеддингов**: Использование легковесных моделей эмбеддингов (например, OpenAI `text-embedding-3-small` или open-source моделей `all-MiniLM-L6-v2` через Hugging Face API).
- **Векторная база данных**: Расширение `pgvector` в существующей PostgreSQL (для минимизации инфраструктурных затрат и сохранения принципа "Zero-Cost").
- **Схема векторизации**:
  - Скрипт транскрибации после завершения расшифровки разбивает текст `transcript.txt` на пересекающиеся чанки (по 1000 символов с перекрытием 200 символов).
  - Для каждого чанка генерируется вектор эмбеддинга.
  - Чанки и их векторы записываются в таблицу `meeting_embeddings` с внешним ключом `meeting_id` и `chat_id`.

### 3. Чат с агентом (Одинарные и Мульти-встречи)
- **Контекст одной встречи**: При входе в чат по конкретной встрече (`meeting_id`) все поисковые запросы пользователя векторизуются, выполняется косинусное сходство (`cos_similarity`) только по записям с данным `meeting_id`. Наиболее релевантные чанки (Top-5) передаются в системный промпт LLM (Groq Llama-3).
- **Мульти-контекстный чат (Несколько встреч)**:
  - Пользователь выбирает несколько встреч через инлайн-кнопки (ID выбранных встреч временно сохраняются в состоянии диалога пользователя).
  - Поисковый запрос пользователя сравнивается со всеми чанками, имеющими `meeting_id IN (выбранные_встречи)`.
  - Извлеченный контекст маркируется метаданными (например, `[Встреча от 2026-06-20]` или `[Спикеры: Павел и Ксения]`), чтобы LLM могла разделять информацию во времени и пространстве.
- **Глобальный поиск о себе ("Диалоги обо мне")**:
  - Поиск осуществляется по всей базе эмбеддингов пользователя (`chat_id`), отфильтрованной по релевантности. Это позволяет ИИ-ассистенту отвечать на сквозные вопросы вроде: "Какая критика в мой адрес звучала на всех встречах за этот месяц?".

### 4. Архитектура лайв-агента во встрече (Real-time Голосовой диалог)
- **Real-time STT и VAD**:
  - Внедренный в Puppeteer код перехватывает смешанный аудиопоток участников встречи.
  - Аудиопоток непрерывно анализируется на хосте с помощью локального VAD (Voice Activity Detection), чтобы определять моменты, когда кто-то говорит.
  - Аудио стримится по протоколу WebSocket в Yandex SpeechKit Streaming или OpenAI Realtime API для мгновенной расшифровки.
- **Инъекция звука (Audio Injection)**:
  - В `recorder.js` внедряется скрипт-перехватчик API `getUserMedia`.
  - При попытке Телемоста захватить микрофон, скрипт возвращает кастомный `MediaStream` с Web Audio нодой `MediaStreamAudioDestinationNode`.
  - ИИ-агент на хосте преобразует сгенерированный текст в аудио-буферы (через потоковый TTS) и отсылает их в браузер через WebSocket-соединение с Puppeteer.
  - Браузер декодирует чанки аудио и проигрывает их напрямую в Web Audio ноду, транслируя голос ИИ во встречу Телемоста.

## Отслеживание сложности

*Сложность находится в рамках разумных архитектурных допущений. Нарушений принципов конституции не выявлено.*

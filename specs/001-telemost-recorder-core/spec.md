## Сценарии использования и тестирование *(обязательно)*

### Пользовательская история 1 - Подключение бота и запись WebRTC аудио (Приоритет: P1)

Бот-рекордер автоматически подключается к существующей конференции Яндекс.Телемост в качестве гостя, устанавливает заданное отображаемое имя, отключает свои виртуальные микрофон и камеру, перехватывает WebRTC-потоки участников и записывает их в единый локальный WebM-файл.

**Почему такой приоритет**: Это фундаментальное ядро всей системы. Без захвата аудиопотока встречи невозможны транскрибация, саммаризация и отправка отчетов.

**Независимый тест**: Запуск `recorder.js` с валидной ссылкой на тестовую конференцию Яндекс.Телемост и проверка того, что бот отображается в списке участников под заданным именем, а после завершения в директории `/recordings` появляется непустой файл `meeting_audio.webm`.

**Сценарии приемки**:

1. **Дано**: Ссылка на активную встречу Телемост и путь для записи файла.
   **Когда**: Запускается процесс `recorder.js` с аргументами `<join_url>` и `<output_file>`.
   **Тогда**: Браузер Puppeteer открывает ссылку в headless-режиме, обходит кнопку "Продолжить в браузере", вводит имя бота из `BOT_DISPLAY_NAME`, отключает микрофон и камеру на панели предпросмотра, нажимает кнопку "Подключиться/Присоединиться".
2. **Дано**: Бот находится в комнате конференции.
   **Когда**: Удаленные участники начинают говорить (появляются входящие WebRTC аудиодорожки).
   **Тогда**: Скрипт монки-патчинга `RTCPeerConnection` перехватывает треки, объединяет их через `AudioContext` в единый поток `MediaRecorder` и сохраняет чанки аудио (каждые 2 секунды) в выходной файл.

### Пользовательская история 2 - Автоматическое завершение и очистка (Anti-Zombie) (Приоритет: P1)

Система гарантирует своевременное отключение бота и закрытие процессов браузера Chromium при завершении встречи, превышении лимитов или получении системных сигналов, исключая появление "зомби-процессов" и утечки ресурсов на сервере.

**Почему такой приоритет**: Предотвращает переполнение оперативной памяти (RAM) и диска сервера из-за зависших headless-процессов Chrome при частых запусках.

**Независимый тест**: Запуск рекордера во встрече без участников и проверка того, что по истечении времени простоя (`MAX_IDLE_MINS`) процесс завершается сам, а в диспетчере процессов отсутствуют незакрытые экземпляры Chromium.

**Сценарии приемки**:

1. **Дано**: Бот находится в комнате конференции один (или с одним участником).
   **Когда**: Время одиночества бота превышает значение `MAX_IDLE_MINS` (по умолчанию 3 минуты).
   **Тогда**: Монитор присутствия завершает цикл ожидания, вызывает функцию `gracefulShutdown`, корректно останавливает запись, закрывает браузер и завершает процесс с кодом 0.
2. **Дано**: Длительность встречи превышает лимит `MAX_DURATION_MINS` (по умолчанию 180 минут).
   **Когда**: Наступает лимит времени записи.
   **Тогда**: Рекордер автоматически останавливает запись и закрывает сессию.
3. **Дано**: Контейнеру рекордера посылается сигнал `SIGINT` или `SIGTERM`.
   **Когда**: Процесс перехватывает сигнал.
   **Тогда**: Выполняется блок `gracefulShutdown`, останавливается `MediaRecorder`, закрывается браузер Puppeteer, локальные дескрипторы освобождаются, и процесс завершается без зависания.

### Пользовательская история 3 - Интеллектуальная транскрибация с фоллбэком на Groq (Приоритет: P2)

Текст разговора распознается с разделением по спикерам (диаризацией). В случае сбоя или отсутствия доступа к основному тяжелому API (AssemblyAI) система автоматически разделяет аудио на фрагменты и отправляет их в более быстрый резервный API (Groq Whisper), восстанавливая хронологию.

**Почему такой приоритет**: Обеспечивает высокую точность расшифровки (с разделением по лицам) и гарантирует отказоустойчивость при превышении лимитов или блокировке основного ИИ-сервиса.

**Независимый тест**: Запуск `transcribe.js` с временным отключением API ключа AssemblyAI. Проверка того, что аудиофайл успешно делится на чанки с помощью FFmpeg и транскрибируется через Groq Whisper с последующей корректной склейкой фрагментов.

**Сценарии приемки**:

1. **Дано**: Записанный аудиофайл `meeting_audio.webm` передан скрипту транскрибации.
   **Когда**: API-ключ AssemblyAI валиден и доступен.
   **Тогда**: Аудио отправляется целиком, возвращается текст с разметкой спикеров (`Спикер 0`, `Спикер 1` и т.д.) и временными метками фраз.
2. **Когда**: AssemblyAI возвращает ошибку или недоступен.
   **Тогда**: Скрипт переключается на резервный путь: с помощью FFmpeg нарезает файл на сегменты (по умолчанию 10 минут) без перекодирования (для экономии CPU).
3. **Дано**: Аудио разделено на сегменты.
   **Когда**: Файлы поочередно отправляются в Groq API (`whisper-large-v3`).
   **Тогда**: Полученные тексты склеиваются с расчетом сдвига времени (`offset = index * segmentLengthSeconds`), формируя единую хронологическую ленту транскрипции.

### Пользовательская история 4 - Выгрузка в облачные хранилища (Яндекс.Диск + S3) (Приоритет: P2)

Результаты встречи (запись аудио и расшифрованный текст) автоматически загружаются в персональное облако пользователя по протоколу WebDAV (Яндекс.Диск) в структурированную папку, а копия аудиофайла может дублироваться в S3-бакет. После успешной загрузки все локальные файлы удаляются с сервера.

**Почему такой приоритет**: Экономит дисковое пространство сервера (Zero-cost хранение) и предоставляет пользователю доступ к материалам в удобном для него облаке.

**Независимый тест**: Вызов скрипта выгрузки и проверка появления файлов `meeting_audio.webm` и `transcript.txt` в папке `Yandex.Telemost.Records/YYYY-MM-DD_MeetingName` на Яндекс.Диске, а также подтверждение удаления локальной папки встречи.

**Сценарии приемки**:

1. **Дано**: Готовы локальные файлы `meeting_audio.webm` и `transcript.txt`.
   **Когда**: Запускается выгрузка на Яндекс.Диск с авторизационными данными WebDAV.
   **Тогда**: Метод проверяет/создает корневую папку `/Yandex.Telemost.Records`, создает подпапку встречи `/Yandex.Telemost.Records/[Дата]_[Тема]` и поочередно загружает файлы методом `PUT`.
2. **Дано**: В `.env` заполнены параметры `S3_ACCESS_KEY` и `S3_SECRET_KEY`.
   **Когда**: Завершается запись встречи.
   **Тогда**: Копия аудиофайла загружается в указанный S3-бакет (например, в Yandex Cloud Object Storage или MinIO).
3. **Дано**: Выгрузка файлов на внешние хранилища завершена успешно.
   **Когда**: Выполняется финальный блок очистки.
   **Тогда**: Исходный аудиофайл, файлы чанков и временный `transcript.txt` безвозвратно удаляются с локального сервера.

### Пользовательская история 5 - Оркестрация через n8n и Telegram (Приоритет: P2)

Пользователь управляет записью и получает готовые отчеты через Telegram-интерфейс бота. Оркестратор n8n отвечает за управление состояниями (FSM), запуск контейнеров на сервере по SSH, вызов транскрибации, саммаризацию через LLM (OpenRouter) и отправку интерактивных сообщений.

**Почему такой приоритет**: Обеспечивает удобный UX для конечного пользователя, изоляцию вычислений и многопользовательскую безопасность (каждая запись идет в изолированном контейнере).

**Независимый тест**: Имитация полного цикла записи через n8n вебхуки: запуск бота -> отправка команды стоп -> получение итогового сообщения в Telegram с выжимкой и ссылкой на Яндекс.Диск.

**Сценарии приемки**:

1. **Дано**: Пользователь отправляет боту в Telegram ссылку на встречу Телемост.
   **Когда**: n8n получает сообщение.
   **Тогда**: Оркестратор проверяет настройки пользователя, подключается по SSH к серверу и запускает Docker-контейнер с уникальным именем `telemost_[chat_id]`.
2. **Дано**: Запись встречи завершена на сервере.
   **Когда**: Контейнер отправляет webhook-уведомление в n8n.
   **Тогда**: n8n запускает скрипт транскрибации на сервере, затем передает текст в OpenRouter для генерации саммари (краткое содержание, задачи, решения) и высылает структурированное сообщение в Telegram со ссылкой на Яндекс.Диск.

### Пользовательская история 6 - Экспериментальная локальная диаризация на базе WebRTC треков (Приоритет: P3 / Гипотеза)

Система анализирует активность и уровень громкости каждого отдельного входящего `MediaStreamTrack` удаленных участников встречи в реальном времени, сопоставляет его с DOM-именем спикера на странице Телемоста и формирует локальный файл метаданных `diarization_map.json` для точной диаризации без использования сторонних API.

**Почему такой приоритет**: Это экспериментальная гипотеза, тестируемая отдельно от основного ядра. В случае успешного тестирования она позволит полностью отказаться от платных ИИ-моделей диаризации и повысить надежность системы.

**Независимый тест**: Запустить тестовый скрипт `scratch/test_tracks.js` с ссылкой на встречу, где разговаривают не менее 2 спикеров, и проверить, что в консоли выводятся правильные события активности отдельных аудио-треков с фиксацией громкости.

**Сценарии приемки**:

1. **Дано**: Бот находится в комнате конференции и получает аудио-треки участников.
   **Когда**: Спикер A говорит в микрофон.
   **Тогда**: Анализатор Web Audio API (`AnalyserNode`) регистрирует всплеск амплитуды (>0.01) на треке Спикера A, фиксируя точное время начала и конца реплики.

### Пользовательская история 7 - Персональное имя бота-помощника в настройках (Приоритет: P2)

Пользователь имеет возможность через меню настроек Telegram-бота задать собственное имя отображения для бота во встрече. Это имя хранится в базе данных оркестратора n8n для конкретного `chat_id` и передается в контейнер рекордера при каждом новом старте записи, изолируя настройки разных пользователей.

**Почему такой приоритет**: Текущий механизм через глобальный файл `.env` на сервере не работает для Docker-контейнеров и нарушает изоляцию пользователей (каждый запуск перезаписывает настройки других). Динамическая кастомизация критична для поддержки параллельного использования системы.

**Независимый тест**: Запуск скрипта `./run_join.sh` с передачей тестового имени (например, `"Бот-Тестер-123"`) в качестве третьего параметра. Проверка в логах рекордера и на странице Телемоста, что бот зашел с именем `"Бот-Тестер-123"`, а не со стандартным `"Telemost Recorder"`.

**Сценарии приемки**:

1. **Дано**: Пользователь задает в Telegram-боте имя "ИИ-Секретарь".
   **Когда**: n8n инициирует сессию записи для этого пользователя по SSH.
   **Тогда**: n8n передает имя третьим аргументом в скрипт `./run_join.sh`, который пробрасывает его через `-e BOT_DISPLAY_NAME="ИИ-Секретарь"` в контейнер, и Chromium входит в Телемост под этим именем.

### Пользовательская история 8 - Быстрый старт по ссылке с inline-кнопкой (Приоритет: P1)

Пользователь пересылает боту в Telegram сообщение, содержащее только ссылку на встречу Яндекс.Телемост (без команд или предварительного вызова Force Reply). Бот автоматически распознает это действие как сигнал к немедленному старту записи и сразу отправляет в ответ сообщение «Начата запись созвона...» с прикрепленной inline-кнопкой «Остановить запись» для мгновенного прекращения процесса при случайной отправке.

**Почему такой приоритет**: Значительно улучшает пользовательский UX (сокращает количество шагов взаимодействия до одного клика) и предотвращает непреднамеренные записи, предоставляя удобную кнопку отмены.

**Независимый тест**: Отправить боту в Telegram ссылку `https://telemost.yandex.ru/j/12345678901234`. Проверить, что бот без задержек отвечает сообщением, содержащим inline-кнопку «Остановить запись», и инициирует Docker-контейнер.

### Пользовательская история 9 - Мульти-запись и защита от дубликатов (Приоритет: P1)

Один пользователь (Telegram ID) имеет возможность запускать и вести запись нескольких различных встреч Яндекс.Телемост параллельно. При этом система блокирует повторный старт записи для одной и той же встречи (уже находящейся в процессе записи), предотвращая запуск дублирующих контейнеров и порчу аудиофайлов.

**Почему такой приоритет**: Обеспечивает стабильность записи при случайных повторных кликах пользователя и гибкость при работе с несколькими параллельными сессиями от одного аккаунта.

**Независимый тест**: 
1. Запустить запись встречи А, затем отправить ссылку на встречу Б. Убедиться, что обе записи работают параллельно в независимых контейнерах.
2. Повторно отправить ссылку на встречу А. Убедиться, что бот отвечает сообщением о том, что встреча уже записывается, и не перезапускает контейнер.

### Пользовательская история 10 - Поэтапная выгрузка и ИИ-переименование папок на Яндекс.Диске (Приоритет: P2)

Система выгружает медиафайлы поэтапно: сразу после записи отправляется аудиодорожка встречи, а после готовности транскрипта — текстовый `.txt` файл. После завершения всех загрузок папка встречи на Яндекс.Диске переименовывается методом WebDAV `MOVE` в ИИ-название на основе содержания встречи и спикеров: при количестве спикеров менее 5 папка включает имена спикеров (например, `Павел_и_Ксения_о_разработке_бота`), а при 5 и более спикерах — общий формат конференции (например, `Конференция_на_тему_оптимизации_бизнес_процессов`).

**Почему такой приоритет**: Обеспечивает пользователю мгновенный доступ к сырым данным, гарантирует высокую читаемость и структурированность структуры каталогов на Яндекс.Диске.

**Независимый тест**: Провести полную запись встречи с 3 спикерами (например, Павел, Ксения, Игорь) и проверить, что сначала на Яндекс.Диск загружается аудио, затем `.txt` файл, а затем папка переименовывается в формат с именами спикеров.

**Почему такой приоритет**: Позволяет пользователям организовывать свои встречи в понятную и удобную структуру папок.

Это позволяет задавать глобальные вопросы (например, "Где и когда я упоминал о разработке Спецификации?" или "Какова динамика по проекту за последние 3 недели?").

### Пользовательская история 15 - Живой разговор с ИИ-агентом внутри Телемоста (Приоритет: P4 / Перспективная)

Пользователь имеет возможность запустить бота в конференцию Телемост в режиме "Активный участник". Бот в реальном времени слушает входящий WebRTC аудиопоток, распознает речь участников (STT), обрабатывает её с помощью LLM-агента и озвучивает ответы (TTS), транслируя свой синтезированный голос обратно в WebRTC-канал встречи. Участники созвона могут общаться с ботом голосом в режиме реального времени.

**Почему такой приоритет**: Это гранд-фича будущего развития продукта, которая выведет бота из роли пассивного слушателя в роль полноценного живого ассистента или модератора переговоров.

---



### Граничные случаи

- **Тишина во время встречи**: Если в комнате есть участники, но они молчат, или никто не включил микрофон. Система продолжит запись, создавая файл минимального размера, но VAD/транскрибация вернут пустой текст. Система должна корректно обработать пустой текст транскрипции и не ломаться при выгрузке.
- **Внезапный обрыв соединения / падение Chromium**: Если вкладка Телемоста зависла или закрылась. Монитор участников должен выбросить ошибку, а блок `finally` в `recorder.js` должен гарантированно закрыть браузер, сохранить записанную часть аудио и вызвать webhook для n8n, чтобы сохранить хотя бы часть записи.
- **Некорректная или битая ссылка**: Бот переходит по ссылке, которая ведет на ошибку 404 или страницу входа. Бот не сможет обнаружить элементы интерфейса встречи. По истечении таймаута Puppeteer в 45 секунд сработает `catch`, браузер закроется, и процесс завершится, сообщив оркестратору об ошибке.
- **Сбой авторизации Яндекс.Диска (WebDAV)**: Неправильный пароль приложения или логин. Выгрузка упадет с ошибкой 401/403. Скрипт транскрибации запишет ошибку в лог, вернет JSON с описанием сбоя в n8n, чтобы оркестратор уведомил пользователя в Telegram о необходимости обновить настройки. Локальные файлы в этом случае НЕ удаляются (чтобы не потерять запись окончательно), давая администратору шанс спасти аудио.
- **Одновременная речь участников (Перебивание)**: Если во встрече говорят два и более человек одновременно, система локальной WebRTC-диаризации должна зафиксировать параллельную активность на соответствующих треках отдельно, создав пересекающиеся временные метки в `diarization_map.json`.
- **Конфликт имен при одновременной записи (Race Condition)**: Если два пользователя запускают запись встреч одновременно с разными настройками имен. Система ДОЛЖНА запускать контейнеры с раздельной передачей переменной `BOT_DISPLAY_NAME` для каждого контейнера, полностью исключая взаимное влияние настроек.

## Требования *(обязательно)*

### Функциональные требования

- **FR-001**: Бот ДОЛЖЕН подключаться к конференциям Яндекс.Телемост в качестве гостя, используя переданный URL-адрес встречи.
- **FR-002**: Бот ДОЛЖЕН устанавливать отображаемое имя во встрече на основе переменной `BOT_DISPLAY_NAME`.
- **FR-003**: Бот ДОЛЖЕН отключать виртуальные микрофон и камеру на странице подготовки (лобби) до входа в конференцию.
- **FR-004**: Бот ДОЛЖЕН перехватывать входящие WebRTC аудиопотоки удаленных участников встречи непосредственно из объекта `RTCPeerConnection` в контексте страницы Puppeteer.
- **FR-005**: Бот ДОЛЖЕН микшировать все входящие аудиопотоки с помощью Web Audio API (`AudioContext` и `MediaStreamDestination`).
- **FR-006**: Бот ДОЛЖЕН записывать объединенный аудиопоток в формате `.webm` с кодеком Opus (битрейт 32kbps) и записывать его чанками по 2 секунды на диск хоста.
- **FR-007**: Бот ДОЛЖЕН автоматически отслеживать количество участников и завершать работу, если он остается один в течение `MAX_IDLE_MINS` (по умолчанию 3 минуты).
- **FR-008**: Бот ДОЛЖЕН завершать запись принудительно при превышении `MAX_DURATION_MINS` (по умолчанию 180 минут).
- **FR-009**: Бот ДОЛЖЕН перехватывать сигналы `SIGINT` и `SIGTERM` для выполнения чистого завершения работы: остановить запись, закрыть вкладки и браузер.
- **FR-010**: По завершении процесса записи, оркестрирующий скрипт `run.js` ДОЛЖЕН отправить HTTP Webhook-запрос на адрес `N8N_WEBHOOK_URL` с метаданными сессии (путь к файлу, имя встречи, chat ID).
- **FR-011**: Оркестрирующий скрипт `run.js` ДОЛЖЕН поддерживать опциональную выгрузку аудиофайла в S3-совместимое хранилище.
- **FR-012**: Скрипт транскрибации `transcribe.js` ДОЛЖЕН поддерживать двухэтапный пайплайн распознавания речи: AssemblyAI в качестве основного провайдера (с автоматической диаризацией на русском языке) и Groq Whisper в качестве резервного.
- **FR-013**: В случае сбоя AssemblyAI, система ДОЛЖНА нарезать WebM файл на чанки по 10 минут с помощью FFmpeg (командой `ffmpeg -f segment -c copy`) для соответствия лимиту размера файлов в Groq (25 МБ).
- **FR-014**: Скрипт транскрибации ДОЛЖЕН вызывать Groq API (`whisper-large-v3`) для каждого чанка последовательно и склеивать результаты в один упорядоченный текст.
- **FR-015**: Скрипт транскрибации ДОЛЖЕН сохранять финальный текст расшифровки в файл `transcript.txt`.
- **FR-016**: Скрипт транскрибации ДОЛЖЕН автоматически создавать на Яндекс.Диске пользователя по протоколу WebDAV структуру папок `/Yandex.Telemost.Records/[Имя_Встречи]/` и загружать туда `meeting_audio.webm` и `transcript.txt`.
- **FR-017**: После успешной выгрузки на Яндекс.Диск система ДОЛЖНА удалить все локальные временные файлы встречи и очистить папку записи на хост-сервере.
- **FR-018**: (Экспериментально) Система ДОЛЖНА поддерживать программный замер уровня громкости каждого входящего `MediaStreamTrack` в реальном времени с интервалом 100-200 мс с помощью `AnalyserNode`.
- **FR-019**: (Экспериментально) Система ДОЛЖНА иметь возможность сопоставлять `track.id` с HTML-элементом `<audio>` в DOM-дереве страницы Телемоста для извлечения отображаемого имени говорящего.
- **FR-020**: Система ДОЛЖНА поддерживать хранение и чтение индивидуального имени бота в настройках пользователя (привязано к `chat_id` в PostgreSQL).
- **FR-021**: Скрипт запуска `run_join.sh` ДОЛЖЕН считывать имя бота из третьего входного аргумента и передавать его при запуске Docker-контейнера через переменную среды `BOT_DISPLAY_NAME`.
- **FR-022**: Оркестратор n8n ДОЛЖЕН автоматически парсить входящие текстовые сообщения со ссылками Яндекс.Телемост как сигнал к началу записи.
- **FR-023**: Бот ДОЛЖЕН отправлять ответное сообщение с inline-кнопкой «Остановить запись», которая имеет callback-данные с уникальным идентификатором встречи.
- **FR-024**: Скрипт запуска `run_join.sh` ДОЛЖЕН формировать имя контейнера как `telemost_${CHAT_ID}_${MEETING_ID}`, где `MEETING_ID` извлекается из URL встречи, обеспечивая поддержку параллельных записей.
- **FR-025**: Скрипт запуска `run_join.sh` ДОЛЖЕН проверять наличие активного контейнера с тем же `MEETING_ID` и блокировать повторные запуски для этой встречи.
- **FR-026**: Система ДОЛЖНА поддерживать поэтапную выгрузку: сначала аудиофайл, затем стенограмму в формате `.txt` в ту же временную папку.
- **FR-027**: Система ДОЛЖНА поддерживать метод WebDAV `MOVE` для переименования папок на Яндекс.Диске.
- **FR-028**: Оркестратор ИИ ДОЛЖЕН подсчитывать количество уникальных спикеров и анализировать тему разговора для генерации итогового имени папки.
- **FR-029**: Итоговое имя папки встречи на Яндекс.Диске ДОЛЖНО соответствовать формату `[Дата]_[Имя_Спикера_1]_и_[Имя_Спикера_2]_[Суть]` при количестве спикеров менее 5, и `[Дата]_Конференция_на_тему_[Суть]` при количестве спикеров 5 и более.
- **FR-030**: Скрипт транскрибации ДОЛЖЕН генерировать бизнес-саммари встречи на основе текста расшифровки по шаблону, сохранять его в файл `summary.txt` на Яндекс.Диске в той же папке и возвращать в итоговом JSON для отправки пользователю.
- **FR-031**: Система ДОЛЖНА поддерживать извлечение списка прошлых сессий записи из базы данных PostgreSQL или путем опроса директорий Яндекс.Диска через WebDAV-метод `PROPFIND`.
- **FR-032**: Бот ДОЛЖЕН предоставлять интерфейс для скачивания/вывода результатов встречи (аудиозапись, стенограмма, саммари в виде текстового сообщения).
- **FR-033**: Система ДОЛЖНА поддерживать кастомное переименование папки встречи на Яндекс.Диске через вызов WebDAV `MOVE` по команде пользователя в Telegram.
- **FR-034**: Система ДОЛЖНА векторизовать (разбивать на перекрывающиеся чанки, генерировать эмбеддинги и сохранять в векторную БД) стенограммы для обеспечения возможности семантического поиска.
- **FR-035**: Чат-агент ДОЛЖЕН поддерживать ведение сессии ответов на вопросы пользователя в контексте одной выбранной встречи на основе RAG-модели.
- **FR-036**: Чат-агент ДОЛЖЕН поддерживать мульти-контекстный RAG для одновременного анализа произвольного количества встреч, выбранных пользователем, или для глобального поиска по всей базе знаний пользователя.
- **FR-037**: Система ДОЛЖНА поддерживать real-time транскрибацию (STT) входящих WebRTC аудиодорожек встречи с задержкой не более 1.5 секунд для мгновенной реакции ИИ-ассистента на речь спикеров.
- **FR-038**: Бот-рекордер ДОЛЖЕН уметь генерировать и транслировать синтезированную речь (TTS) в конференцию Яндекс.Телемост в реальном времени путем подмены медиаустройств в браузере (Monkey patching `navigator.mediaDevices.getUserMedia`).




### Ключевые сущности

- **Сессия записи (Recording Session)**: Представляет собой запуск контейнера для одной встречи. Характеризуется уникальным `chat_id` пользователя, датой запуска, URL-адресом встречи и статусом записи.
- **Аудиофайл встречи (WebM Audio)**: Локальный файл, содержащий аудиозапись встречи в формате WebM Opus.
- **Сегмент аудио (Chunk)**: 10-минутный фрагмент аудиофайла встречи, создаваемый FFmpeg для резервной транскрибации.
- **Транскрипт встречи (Transcript)**: Текстовый файл расшифровки встречи. Содержит реплики спикеров с указанием их меток (например, "Спикер A", "Спикер B") и временных интервалов.
- **Хранилище WebDAV (Yandex Disk)**: Облачное хранилище пользователя, куда выкладываются финальные медиа- и текстовые файлы.

## Критерии успеха *(обязательно)*

### Измеримые результаты

- **SC-001**: Бот подключается к встрече и начинает запись в течение 10–15 секунд с момента отправки ссылки пользователем в Telegram.
- **SC-002**: Локальные файлы полностью удаляются с сервера после успешной выгрузки в облако, обеспечивая 0 МБ остаточного дискового пространства на встречу.
- **SC-003**: При сбое основного провайдера AssemblyAI резервная транскрибация через Groq запускается автоматически и завершает расшифровку 1 часа аудио менее чем за 3 минуты.
- **SC-004**: Доля успешных завершений сессий записи при корректных ссылках составляет не менее 98% (отсутствие зомби-процессов Chrome).
- **SC-005**: Поддержка встреч длительностью до 180 минут без падения Puppeteer по памяти (утечек памяти Chromium в headless-режиме).
- **SC-006**: (Экспериментально) Точность локальной разметки активных спикеров по WebRTC-трекам составляет не менее 99% при отсутствии критического шума на микрофонах участников.
- **SC-007**: Бот реагирует на отправленную ссылку и отправляет сообщение с кнопкой отмены в течение 2 секунд.
- **SC-008**: Система позволяет осуществлять неограниченное число параллельных записей встреч от одного Telegram ID, лимитированное только ресурсами хост-сервера.
- **SC-009**: Время переименования папки на Яндекс.Диске после завершения всех этапов выгрузки составляет не более 3 секунд.

## Предположения и допущения

- У пользователя есть стабильное интернет-подключение и корректные учетные данные Яндекс.Диска (логин и пароль приложения WebDAV), сохраненные в БД n8n.
- Сервер имеет установленный FFmpeg, доступный глобально через переменную среды PATH.
- Для корректного перехвата WebRTC аудио встречи в Яндекс.Телемосте используется Puppeteer с отключенным sandbox на Linux/Windows.
- Наличие API ключей `GROQ_API_KEY` и `ASSEMBLYAI_API_KEY` в системном окружении или файле `.env` на сервере.
- Встречи Яндекс.Телемост не требуют дополнительного ввода пароля или подтверждения личности бота организатором (или бот ожидает в лобби до подтверждения).
